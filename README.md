# PII Detector and Risk Dashboard

Scans a folder of emails and documents, finds personal data (PII), scores every file **High / Medium / Low / Clean**,
estimates illustrative compliance exposure under **India's DPDP Act 2023** and the **EU GDPR**, and presents it all in
an interactive Streamlit dashboard, with redacted copies of the riskiest files as a remediation example.

> **All sample data in this project is synthetic.** Names, Aadhaar numbers, PANs, bank accounts, phone numbers and
> salaries are generated by `src/generate_sample_data.py` with Faker (en_IN) and random numbers. The identifiers follow
> official formats (Aadhaar numbers pass the Verhoeff checksum) but belong to nobody.

---

## The business problem

Most companies cannot say where personal data sits in their email and file shares. Aadhaar numbers get pasted into
support tickets, payroll spreadsheets get emailed around, and medical certificates sit in HR inboxes for years. That
creates **legal risk** (DPDP and GDPR require protecting data and deleting it when it is no longer needed), **breach
risk** (you cannot protect what you have not found), and **AI-readiness risk** (you cannot safely feed documents into
GenAI search if you do not know which ones hold personal data). This project shows the first three steps of information
governance: **discover** where PII is, **classify** how risky each file is, and **remediate** the worst of it.

## Quick start

You need **Python 3.11** (3.10 and 3.12 also work) and an internet connection for the first install (~1 GB including
the spaCy language model).

### Windows (one click)

1. Install Python 3.11 from https://www.python.org/downloads/ and tick **"Add python.exe to PATH"**.
2. Double-click **`run_demo.bat`** (or run it from Command Prompt in the project folder).

### macOS / Linux (one click)

```bash
cd pii-risk-dashboard
./run_demo.sh
```

Both scripts: create `.venv` → install `requirements.txt` → download the spaCy model (`en_core_web_lg`, falling back to
`en_core_web_sm` automatically) → generate the sample data → run the scan → run the tests → launch the dashboard.

### Step by step (any OS)

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate            # Windows
source .venv/bin/activate         # macOS / Linux

# 2. Install
pip install -r requirements.txt
python -m spacy download en_core_web_lg     # if this fails: python -m spacy download en_core_web_sm

# 3. Generate data, scan, test, view
python -m src.generate_sample_data
python -m src.scan --source sample
python -m pytest
streamlit run dashboard/app.py
```

If the dashboard opens before any scan exists, it shows the commands above and a **"Run sample scan now"** button.

## Scanning your own data

### Any folder

```bash
python -m src.scan --source folder --path "C:\Users\me\Documents\export"      # Windows
python -m src.scan --source folder --path ~/Documents/export                  # macOS
```

Supported: `.eml`, `.msg`, `.txt`, `.csv`, `.xlsx`, `.docx`, `.pdf` (sub-folders included). Files that cannot be read
are listed as *skipped* with the error; they never stop the scan. Put real data in `data/raw/` (it is git-ignored).

### Enron email dataset

1. Download **"Enron Email Dataset"** by *wcukierski* from Kaggle (https://www.kaggle.com/datasets/wcukierski/enron-email-dataset).
2. Unzip and place `emails.csv` in `data/raw/`.
3. Run:

```bash
python -m src.scan --source enron --path data/raw/emails.csv --limit 5000
```

The full file has ~500,000 emails; `--limit` (default 5000) reads only the first N rows, streaming the file so memory
use stays low. Each message is parsed into sender, recipients, date, subject and body.

### Options

| Option | Meaning |
|---|---|
| `--limit N` | scan at most N documents |
| `--workers N` | parallel processes (default 1 on Windows, 2 elsewhere); each loads the spaCy model once |
| `--min-score 0.6` | discard findings below this confidence (default 0.5, from `config.yaml`) |
| `--no-redact` | skip writing redacted copies |
| `--output-dir PATH` | write the database/exports somewhere other than `output/` |

### Outputs

| Path | Contents |
|---|---|
| `output/pii_results.db` | SQLite: `scans`, `documents`, `findings`, `skipped`, `redactions` |
| `output/exports/documents.csv` | one row per document with score, level, reason (for Excel / Power BI) |
| `output/exports/findings_summary.csv` | per document × entity type: count and confidence |
| `output/exports/entity_counts.csv` | per entity type: findings, documents, unique values |
| `output/exports/accuracy.csv` | precision/recall per entity type (when a `ground_truth.csv` exists) |
| `output/redacted/` | the 10 riskiest documents with values replaced by `<ENTITY_TYPE>` tags |
| `output/scan.log` | processing log (file names and counts only, never values) |

Only **masked** values (e.g. `XXXX XXXX 1234`, `r****@gmail.com`) are ever stored, logged or shown.

## What it detects

| Entity | How it is found |
|---|---|
| `IN_AADHAAR` | 12 digits (optional 4-4-4 spacing), first digit 2-9, **Verhoeff checksum** must pass |
| `IN_PAN` | `AAAAA9999A`, 4th letter must be a valid holder type (P, C, H, F, A, T, B, L, J, G) |
| `IN_IFSC` | `AAAA0XXXXXX` (bank code, literal 0, branch code) |
| `IN_PHONE` | Indian mobiles starting 6-9, optional `+91` / `0` prefix |
| `IN_UPI` | `name@handle`, only for known UPI handles (`@okaxis`, `@ybl`, …), so normal emails are not flagged |
| `BANK_ACCOUNT` | 9-18 digits **only** when words like *account, a/c, acct, bank* are nearby |
| `SALARY` | ₹ / Rs / INR / $ / lakh / LPA amounts **only** near *salary, CTC, pay, bonus, package…* |
| `HEALTH_INFO` | medical vocabulary (diagnosis, prescription, surgery, diabetes, pregnancy…) |
| `PERSON` | spaCy NER, plus a name-cue recognizer for "Dear X Y", "Customer X Y", "Name: X Y" |
| Built-ins | `EMAIL_ADDRESS`, `PHONE_NUMBER`, `CREDIT_CARD` (Luhn), `US_SSN`, `IBAN_CODE`, `IP_ADDRESS`, `LOCATION`, `DATE_TIME` |

When detectors overlap, a single resolver decides. Structured identifiers (pattern plus checksum or context) beat fuzzy
NER spans, and spaCy spans are trimmed so they never swallow a phone number. For ambiguous numbers, **the nearest label
wins**: a Luhn- or Verhoeff-valid number right after "Account No:" is treated as a bank account.

## How risk scoring works

**File score = Σ (weight × confidence) for every finding + volume bonus, capped at 100.**

| Entity | Weight | | Entity | Weight |
|---|---|---|---|---|
| IN_AADHAAR | 10 | | IN_UPI | 6 |
| CREDIT_CARD | 10 | | IN_PHONE | 4 |
| US_SSN | 10 | | PHONE_NUMBER | 4 |
| HEALTH_INFO | 9 | | IN_IFSC | 3 |
| IN_PAN | 8 | | EMAIL_ADDRESS | 2 |
| BANK_ACCOUNT | 8 | | IP_ADDRESS | 2 |
| IBAN_CODE | 8 | | PERSON | 1 |
| SALARY | 7 | | DATE_TIME, LOCATION | stored, not scored |

* **Volume bonus**: +10 at 10+ sensitive records (weight ≥ 6) in one file, +20 at 50+, +30 at 200+. A payroll sheet
  with 200 Aadhaar numbers is far worse than one email with one.
* **Toxic combination**: a person or identifier (name, Aadhaar, PAN, email, phone) **together with** health, salary or
  financial data is forced to at least **High**, because that pairing is what harms an individual in a breach.
* **Levels**: High ≥ 40 · Medium ≥ 15 · Low > 0 · Clean = no scored findings.
* Each file gets a plain-English reason, e.g. *"146 Aadhaar numbers + 146 PANs + … ; salary details and financial
  account data linked to a named person (toxic combination); bulk file with 584 sensitive records (+30 volume bonus)"*.

All weights, thresholds and penalty figures live in `config.yaml`.

## Compliance view (illustrative)

* **DPDP Act 2023**: the Act does not define a separate "sensitive" category; everything is personal data. The tool flags
  identity, financial and health data as higher risk. Ceiling shown: **up to ₹250 crore** for failing to take reasonable
  security safeguards (a ceiling, not a prediction).
* **GDPR**: ordinary personal data vs **Article 9 special category** (health). Ceiling: **€20 million or 4% of worldwide
  annual turnover, whichever is higher**. Enter a hypothetical turnover in the dashboard.
* **Exposure index (0-100)**: 60 points for scale (log of estimated unique individuals, relative to 100,000) plus
  40 points for severity (share of PII-bearing files that are High risk, Medium counts half).
* Unique individuals are counted without storing PII. Each identifier is turned into a keyed hash (HMAC) using a random
  per-scan key that is never saved, and only the counts are kept. The estimate is conservative: the largest unique count
  of any single identifier type.

*Illustrative estimate for demonstration only, not legal advice.*

**Risk-tier agreement: 98%** of files land in the tier they were generated for:

| Planted tier ↓ / Predicted → | High | Medium | Low | Clean |
|---|---|---|---|---|
| High | 75 | 0 | 0 | 0 |
| Medium | 0 | 85 | 5 | 0 |
| Low | 0 | 0 | 40 | 0 |

Scan totals: 300 documents in 22.5 s on a laptop (2 worker processes), 1 corrupt file skipped,
15,095 findings, 8,750 unique identifiers (at least
2,247 individuals), exposure index 63.0/100.

What the numbers mean: every structured identifier (Aadhaar, PAN, IFSC, phone, UPI, bank account, salary, card)
is found in every file where it was planted, with no false positives. **Names are the weak spot** (recall
0.89): spaCy misses unusual Indian names that no cue word introduces. The Medium files
predicted as Low are callback lists where every phone and email was found but one missed name left the score just
under 15; the one Clean file predicted as Low is a project update in which spaCy tagged an ordinary word as a person
(the single PERSON false positive).

## Results on real data: the Enron emails

Enron's mailboxes were made public by US regulators (FERC) during the investigation into the company's 2001 collapse,
and they have been the standard eDiscovery test set ever since. Run with
`python -m src.scan --source enron --path data/raw/emails.csv --limit 5000` (`en_core_web_lg`, 2 workers). There is no
answer key for Enron, so these are observations, not accuracy figures.

| Metric | Value |
|---|---|
| Emails scanned | 5,000 (0 skipped) in 164 s |
| Emails with PII | 4,284 (86%) |
| Risk levels | 266 High · 516 Medium · 3,502 Low · 716 Clean |
| Toxic combinations | 125 emails |
| Unique email addresses (≈ individuals) | 1,203 |
| Exposure index | 41.9 / 100 (Moderate) |
| Indian identifiers (Aadhaar, PAN, UPI, IFSC) | 0, as expected on US data |

The first 5,000 rows of the Kaggle file cover only two mailboxes, so this is a slice, not a sample of the whole company.

What the real data showed:

* **True positive.** An employee emailed a personal Visa number, expiry date and home address from a work account to
  pay for an eBay purchase. The card passed the Luhn check and was flagged. Personal financial data sitting in a corporate
  mailbox is exactly the risk this tool is meant to surface.
* **False positive: SSN.** One "US SSN" was the first part of a longer contact number (`XXX-XX-1642-718309`). Fix:
  reject a match when more digits follow it.
* **False positive: health keywords.** Spam ("want to lose weight?"), a movie-listings newsletter and a fantasy
  football newsletter were tagged as health data, and the toxic-combination rule then pushed some to High. Fix:
  require medical context, as the bank-account and salary recognizers already do, and down-weight newsletters.
* **Names inflate scores.** Many High files are news digests and an audit summary with 100+ names, mostly public
  figures rather than private individuals.
* **Misses.** Some US phone formats such as `(713) 646-8235` were not detected, and street addresses have no
  recognizer at all.
* **Duplicates.** Only about half of the 5,000 emails are unique: the same message is stored in `sent_mail`,
  `all_documents` and `discussion_threads`. Each copy carries the same PII and is scanned, stored and reviewed again,
  which is why enterprise archives deduplicate before governing.

## Limitations

* **Synthetic data flatters the model.** The templates are regular, so real-world accuracy will be lower. Names are the
  hardest part: spaCy's English model misses many Indian names unless a cue word ("Dear", "Name:") precedes them.
* **Regex false positives.** A random 12-digit number passes the Aadhaar checksum 1 time in 10, and a random 16-digit
  number passes Luhn 1 time in 10. Context rules reduce this but cannot remove it.
* **Enron is US data.** Expect almost no Aadhaar/PAN/UPI there; its value is testing scale, email parsing and names,
  emails, phone numbers and US identifiers on real, messy text.
* **No OCR**: scanned PDFs and images are not read. Email attachments inside `.eml` files are not opened.
* **Penalty figures are statutory ceilings**, used for illustration only; real penalties depend on many factors.
* Sender addresses are stored as custodian metadata (needed for "who sends the most sensitive data"); the *contents*
  of documents are only ever stored masked.

## How this relates to enterprise information governance

| Governance step | In this project | At enterprise scale |
|---|---|---|
| **Data discovery** | recursive scan of folders / mailboxes | connectors to Exchange, SharePoint, file shares, Teams, archives |
| **Classification** | entity detection + risk tiers + reasons | policy-driven classification, custom lexicons, ML models, human review queues |
| **Compliance mapping** | DPDP / GDPR categories, exposure index | records retention schedules, legal hold, DSAR (data subject request) search |
| **Remediation** | redacted copies, action list | automated redaction, access restriction, quarantine, defensible deletion |
| **AI readiness** | "Clean" files identified | only governed, PII-free content flows into GenAI / RAG pipelines |

## Project structure

```
pii-risk-dashboard/
  config.yaml              every weight, threshold and penalty figure
  run_demo.bat / .sh       one-click demo
  src/
    generate_sample_data.py  synthetic Indian corporate dataset + ground truth
    ingest.py                file walking, text extraction, Enron loader
    recognizers.py           custom Presidio recognizers (Verhoeff etc.)
    detector.py              one AnalyzerEngine, masking, overlap resolution, multiprocessing
    risk.py                  scoring, toxic combination, reasons
    compliance.py            DPDP/GDPR mapping, exposure, remediation actions
    redact.py                presidio-anonymizer redacted copies
    storage.py               SQLite schema + CSV exports
    scan.py                  CLI entry point
  dashboard/app.py         Streamlit dashboard
  tests/                   pytest suite
```

## Running the tests

```bash
python -m pytest
```

The suite covers the recognizers (valid/invalid Aadhaar checksums, PAN, IFSC, UPI vs email, salary and bank account
with and without context), risk scoring (thresholds, toxic rule, cap), ingestion of every file type including corrupt
files, and an end-to-end run. The end-to-end test generates 30 files, scans them, checks the database/CSVs/redactions,
checks that no raw Aadhaar or PAN leaked into any output, and renders the dashboard headlessly.
